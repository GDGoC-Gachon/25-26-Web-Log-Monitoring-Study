## 회의 목적

- 브루트포스, 민감 경로 접근, DDoS성 요청 탐지와 메일 알림을 실제 서버 환경에서 시연한다.
- 현재 구현 범위와 오동작 후보를 확인한다.
- 방화벽 등록 자동화와 로그인 기반 관제 웹을 포함한 2차 개발 방향을 논의한다.

## 회의에서 확인된 시연 결과

- 관리·어드민·마스터 등 민감 경로 접근 탐지 코드가 서버에 배포되어 동작 중이라고 공유되었다.
- 잘못된 계정 정보로 인증 실패를 반복해 브루트포스 탐지와 메일 수신을 확인했다.
- 기본 1분 폴링 특성상 초기에는 메일이 지연 또는 미수신처럼 보였으나, 이후 로그와 메일이 정상 수신되었다.
- 약 4,751건의 반복 요청으로 민감 경로 접근과 DDoS성 요청이 탐지되는 것을 확인했다.
- 메일에 공격 IP와 공격 대상 도메인이 표시되는 것을 시연 환경에서 확인했다.

> 4,751건은 시연 입력값이며 제품의 고정 임계값이 아니다. 운영 임계값은 환경 설정과 QA 결과로 결정한다.

## 회의에서 제기된 문제와 개선 요청

- 브루트포스 시나리오에서 서로 다른 도메인의 이벤트가 함께 발생할 때 오동작 가능성이 있어 재현 QA가 필요하다.
- 인증 관련 4xx가 브루트포스 탐지와 웹 오류 탐지에 동시에 포함되어 알림이 중복 또는 혼재될 수 있다.
- Elastic 유저 API 호출부의 개선 범위와 API 계약을 구체화해야 한다.
- 메일 형식을 읽기 쉽게 개선해야 한다.
- 시연 환경의 메일 내용과 현재 저장소 코드의 출력이 일치하는지 확인해야 한다.

## 회의 결정 사항

1. 1차 구현 범위는 탐지와 메일 알림까지로 정의한다.
2. 다음 단계에서는 탐지된 대상을 방화벽에 등록하는 대응 자동화를 개발 방향에 포함한다.
3. 사용자가 Elasticsearch에 직접 접속하는 방식보다, 인증된 사용자가 자신의 서버 IP와 도메인을 등록하고 허용된 대시보드만 조회하는 SaaS형 관제 웹을 검토한다.
4. 오동작 및 수정 사항을 문서로 공유한 뒤 참여자가 투표로 담당 파트를 선택한다.
5. SaaS 웹 제안은 수정 사항과 함께 공유하고 다음 회의에서 범위와 우선순위를 다시 결정한다.

## 회의 액션 아이템

- [ ] 서로 다른 도메인의 브루트포스 이벤트를 동시에 발생시켜 집계·메일 수신 범위를 재검증한다.
- [ ] 전체 탐지 기능을 다시 QA하고 오동작 목록과 증적을 공유한다.
- [ ] Elastic 유저 API의 현재 호출 방식, 문제, 필요한 변경 계약을 정리한다.
- [ ] 알림 메일의 정보 구조와 표현 형식을 개선한다.
- [ ] 인증 기반 SaaS 관제 웹 제안에 대한 의견을 수집한다.
- [ ] 후속 개발 참여자를 확인하고 파트 분담 투표를 진행한다.
- [ ] 다음 회의에서 미결정 사항과 3~4주 검증 범위를 확정한다.

## 회의 후 코드 대조 분석

아래 내용은 회의 발언이 아니라 2026-07-11 `main` commit `7ad79f8`을 대조해 추가한 분석이다. 회의 시연은 배포 환경 기준의 관찰이므로 재현 전까지 확정 결함으로 단정하지 않는다.

- 브루트포스 집계는 이미 `clientIp + hostDomain` 조합으로 분리되어 있으나 다중 도메인 회귀 테스트가 없다.
- 도메인별 수신자를 선택한 뒤 전체 알림 묶음을 같은 본문으로 전송하므로, 다중 도메인 알림이 한 주기에 발생할 때 다른 도메인 정보가 함께 전달될 가능성이 있다.
- DDoS 결과는 도메인별 요청 수를 내부에 보유하지만 현재 기본 메일 본문에는 이를 표시하지 않는다.
- Elastic 유저 API 연동, 방화벽 등록, 로그인 웹, 사용자별 IP·도메인 등록 및 대시보드는 구현되어 있지 않다.
