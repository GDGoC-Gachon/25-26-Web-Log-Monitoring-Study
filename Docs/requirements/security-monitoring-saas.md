## 제품 가설

사용자에게 Elasticsearch 접속 정보와 대시보드 구성 책임을 직접 주는 것보다, 인증된 사용자가 자신의 서버 IP와 `hostDomain`을 등록하고 허용된 탐지·대시보드만 조회하는 웹 서비스가 운영과 보안 측면에서 더 실용적이다.

이 문서는 검토용 MVP 스펙이다. 파트 분담과 다음 회의 승인 전에는 확정 구현 범위로 취급하지 않는다.

## 사용자 스토리

- 서비스 사용자는 로그인해 자신이 담당하는 서버 IP와 도메인을 등록하고 싶다.
- 서비스 사용자는 자신에게 허용된 도메인의 탐지 현황과 근거만 보고 싶다.
- 운영자는 사용자와 모니터링 대상의 관계를 승인·변경·회수하고 싶다.
- 운영자는 전체 탐지와 후속 대응 상태를 한 곳에서 확인하고 싶다.

| REQ-SAAS-004 | 사용자는 자신에게 활성 권한이 있는 모니터링 대상의 데이터만 조회해야 한다. | 검토 중 |
| REQ-SAAS-005 | 운영자는 사용자, 대상, 권한과 활성 상태를 관리할 수 있어야 한다. | 검토 중 |

| REQ-SAAS-010 | 메일 알림과 웹 대시보드는 같은 대상 권한 모델을 사용해야 한다. | 검토 중 |

## 개념 데이터 모델

| 엔터티 | 핵심 정보 |
|--------|-----------|
| User | 안정적인 사용자 ID, 이메일, 활성 상태 |
| MonitoringTarget | 서버 IP, 정규화된 `hostDomain`, 검증 상태 |
| TargetMembership | User와 MonitoringTarget의 역할·상태 관계 |
| DetectionIncident | 유형, 대상, IP, 시간 창, 근거, 상태 |
| NotificationDelivery | 사건, 수신자, 채널, 발송 결과 |
| FirewallAction | 사건, IP, 승인·실행·해제 상태 |
| AuditLog | 행위자, 작업, 대상, 결과, 시각 |

구체 DB와 프레임워크는 기술 검토 후 결정한다.

## 3~4주 검토 범위 제안

기간은 확정 일정이 아니라 타당성 검증 상한으로 사용한다.

1. 인증과 사용자 세션
2. IP·도메인 등록 요청 및 운영자 승인
3. 서버 측 권한 필터를 적용한 읽기 전용 탐지 목록·상세
4. 최소 대시보드와 타 도메인 접근 차단 테스트
5. 운영 배포, 자동 방화벽 변경, 고급 시각화는 별도 승인

## MVP 완료 조건

- 두 서비스 사용자가 서로 다른 도메인을 보유한 시드 데이터로 격리 테스트를 통과한다.
- 미인증, 권한 없음, 비활성 권한의 API 요청이 각각 일관되게 거부된다.
- 브라우저 응답과 클라이언트 번들에 Elastic 자격 증명이 포함되지 않는다.
- 운영자가 사용자-대상 권한을 부여하고 회수할 수 있다.
- 동일 권한 모델로 대시보드 조회와 메일 본문 범위를 계산할 수 있다.

## 미결정 사항

- 인증 공급자와 가입·승인 정책
- 도메인 소유권 검증 방식
- 사용자와 Elastic 계정의 관계 및 Elastic 유저 API 필요 여부
- 자체 대시보드 또는 Kibana 임베드 여부
- 원시 로그 노출 범위와 보관 기간
- 멀티테넌트 데이터 저장·쿼리 격리 방식
