회의에서 직접 제기된 사항은 다중 도메인 오동작과 탐지 중복·혼재다. 사건 ID, cooldown, Job 격리, 폴링 중첩 방지는 현재 코드 분석에서 도출한 후속 설계 제안이며 구현 전에 승인해야 한다.

## 목표

여러 탐지 Job과 여러 도메인의 결과를 안전하게 사건으로 묶고, 겹치는 폴링 구간에서도 중복 발송과 타 도메인 정보 노출 없이 알림을 전달한다. 한 Job의 장애가 전체 탐지 주기를 중단시키지 않도록 한다.

## 현재 상태

- 모든 Job 결과를 하나의 `alerts` 배열로 합친 뒤 한 번의 메일 함수에 전달한다.
- 기본 1분 폴링에서 최근 5분 로그를 매번 다시 조회한다.
- 영속 사건 ID, cooldown, 발송 이력, Job별 장애 격리, 폴링 중첩 방지가 없다.
- 브루트포스와 웹 오류가 같은 인증 4xx를 독립적으로 집계한다.

## 요구사항

| ID | 요구사항 | 상태 |
|----|----------|------|
| REQ-ALERT-001 | 각 탐지 결과는 유형, 발생 시간 창, 출발 IP, 대상 범위를 조합한 추적 가능한 사건 식별 정보를 가져야 한다. | 계획 |
| REQ-ALERT-002 | 모든 알림은 `hostDomain`, `apiDomain`, 다중 도메인 또는 운영자 전용 중 하나의 명시적 대상 범위를 가져야 한다. | 계획 |
| REQ-ALERT-003 | 수신자에게 전달하는 본문은 해당 수신자가 조회 권한을 가진 알림만 포함해야 한다. | 계획 |
| REQ-ALERT-004 | 같은 사건이 겹치는 조회 창에 다시 포함되어도 설정된 cooldown 안에는 재발송하지 않아야 한다. | 계획 |
| REQ-ALERT-005 | 같은 원시 이벤트가 브루트포스와 웹 오류 등 여러 탐지를 충족하면 승인된 상관 정책에 따라 하나의 사건으로 추적해야 한다. | 결정 대기 |
| REQ-ALERT-006 | 한 Job 실패가 다른 Job 실행과 이미 생성된 알림 발송을 막지 않아야 하며, 이전 폴링이 끝나기 전에 다음 폴링을 중첩 실행하지 않아야 한다. | 계획 |
| REQ-ALERT-007 | 폴링 실행 ID, Job별 성공·실패·소요 시간, 생성 사건 수, 메일 결과를 인증 정보 없이 기록해야 한다. | 계획 |

## 수용 기준

| ID | Given | When | Then |
|----|-------|------|------|
| AC-ALERT-001 | A와 B 도메인 알림이 같은 폴링에 존재 | A 도메인 사용자 메일 생성 | 본문과 제목에 B 도메인·IP·경로가 포함되지 않음 |
| AC-ALERT-002 | 동일 사건 로그가 연속 5개 조회 창에 포함 | cooldown 동안 폴링 5회 실행 | 최초 통지 외 반복 메일이 없고 억제 횟수가 기록됨 |
| AC-ALERT-003 | 브루트포스와 웹 오류가 같은 인증 실패 로그로 임계값 충족 | 알림 생성 | 두 탐지의 관계를 추적할 수 있고 승인된 정책보다 많은 메일을 보내지 않음 |
| AC-ALERT-004 | DDoS Job의 Elastic 요청 실패 | 같은 폴링의 다른 Job 실행 | 다른 Job 결과는 발송되고 DDoS 실패가 별도로 기록됨 |
| AC-ALERT-005 | 한 폴링이 실행 중 | 다음 예약 시각 도달 | 두 번째 실행을 건너뛰거나 대기열에 넣고 중첩하지 않음 |

## 미결정 사항

- 사건 식별 키와 저장 위치
- 탐지 유형별 cooldown과 재통지 조건
- 브루트포스와 4xx를 합칠지, 한 사건의 연관 항목으로 나란히 표시할지
- 다중 도메인 DDoS를 도메인별 사건으로 분할할지 운영자 전용으로 둘지
- 프로세스 재시작 후에도 발송 이력을 유지할지
