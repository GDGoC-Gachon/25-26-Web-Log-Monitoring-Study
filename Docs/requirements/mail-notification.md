| REQ-MAIL-011 | 폴링·사건 ID와 수신자별 발송 성공·실패를 감사 가능하게 추적해야 한다. | 계획 |

## 현재 구현 경계

각 탐지 결과는 별도 HTML 및 plain-text 메일로 렌더링한다. role이 탐지 도메인과 정확히 일치하는 사용자는 `To`, `superuser` role 사용자는 envelope BCC로 넣는다. 사용자 API 요청이 실패하거나 타임아웃되면 `mail_notification_user_lookup_failed`만 기록하고 해당 폴링에서는 SMTP에 연결하지 않는다.

원본 Elastic 사용자 응답, 사용자 API 오류 문자열, SMTP 자격 증명은 로그에 기록하지 않는다. 실제 운영 API 권한과 메일함 수신은 [회귀 QA](../test-plans/2026-07-06-detection-regression.md)로 별도 확인한다.

## 수용 기준

| ID | 시나리오 | 기대 결과 |
|----|----------|-----------|
| AC-MAIL-001 | 알림 없음 | SMTP 연결과 메일 발송 없음 |
| AC-MAIL-002 | A와 B 알림 동시 발생 | A role 사용자는 A만, B role 사용자는 B만 `To`로 수신 |
| AC-MAIL-003 | 같은 상황에서 `superuser` 수신 | 각 탐지 메일의 SMTP envelope BCC로 수신하고 `Bcc` 헤더는 없음 |
| AC-MAIL-004 | 여러 도메인 DDoS | 운영자 본문에 도메인별 요청 수 표시 |
| AC-MAIL-005 | SMTP 인증 또는 네트워크 실패 | 실패가 기록되고 자격 증명은 기록되지 않음 |
| AC-MAIL-006 | HTML을 표시하는 메일 클라이언트 | 탐지별 유형·대상·심각도·근거·권장 조치를 시각적으로 구분 |
| AC-MAIL-007 | HTML을 표시하지 않는 메일 클라이언트 | plain-text 본문에서 같은 핵심 정보 확인 |
| AC-MAIL-008 | 경로나 오류 사유에 `<`, `>`, `&`, 따옴표가 포함됨 | 텍스트로 표시되고 HTML 구조나 링크를 주입하지 않음 |
| AC-MAIL-009 | Elastic 사용자 API 실패 또는 타임아웃 | SMTP 연결과 발송이 없고 비밀정보 없는 오류만 기록 |

## 발송 시점

“즉시 알림”은 탐지 결과가 만들어진 뒤 지체 없이 발송을 시도한다는 의미다. 로그 발생 시점 기준으로는 다음 정상 폴링과 Elastic 조회가 끝난 뒤 발송되므로, 실제 도착 지연은 폴링 주기와 외부 시스템 처리 시간을 포함해 QA에서 측정한다.
