# 오류 및 기능개선 사항 반영 기록

| 항목 | 내용 |
|------|------|
| 원본 | `오류 및 기능개선 사항.pdf` |
| 원본 작성자 | 박준호(PDF 메타데이터) |
| 원본 생성일 | 2026-07-11(PDF 메타데이터) |
| 반영일 | 2026-07-13 |
| 문서 성격 | 제보·개선 요청의 추적 기록 |
| 상위 스펙 | [모니터링 시스템 통합 스펙](../monitoring-system-specification.md) |

이 문서는 PDF에 적힌 현상과 요청을 현재 코드에 대조한 기록이다. PDF의 직접 요청, 코드에서 확인한 현재 상태, 확정된 결정과 남은 결정 항목을 구분한다.

## 1. 원본 요청

| ID | 구분 | PDF의 내용 | 요청 결과 |
|----|------|------------|-----------|
| FEEDBACK-001 | 오류 | 폴링 주기와 조회 창을 1분으로 두고 한 도메인에서 4xx 또는 5xx가 1건만 발생해도 오류율이 100%가 되어 경고 메일이 발송됨 | 오류율 임계값을 적용하기 전에 도메인·집계 키별 최소 트래픽 수를 충족하도록 하한선 추가 |
| FEEDBACK-002 | 기능 개선 | 현재 경고 메일이 별도 서식 없는 본문이어서 여러 탐지를 빠르게 읽기 어려움 | HTML 스타일을 지원하는 읽기 쉬운 메일 템플릿 검토. 기존 SMTP의 HTML MIME 또는 Resend 템플릿 사용 가능성 검토 |
| FEEDBACK-003 | 기능 개선 | `SMTP_TO` 수신자가 모든 경고를 받고 서비스 사용자의 도메인별 수신 범위를 자동 관리할 수 없음 | Elastic 사용자 정보의 `roles`와 `email`을 사용해 운영자와 서비스 사용자의 수신 범위를 구분 |

## 2. PDF에 제시된 Elastic 사용자 계약

PDF의 개발 요구서 화면에는 다음 후보 계약이 제시되어 있다.

| 항목 | 제시 내용 |
|------|-----------|
| 메서드·경로 | `GET https://api.gdgoc.net/_security/user` |
| 인증 | Elastic 계정 기반 Basic Auth |
| 응답 구조 | 사용자명을 키로 하고 `username`, `roles`, `full_name`, `email`, `metadata`, `enabled`를 포함하는 JSON 객체 |
| 전체 수신자 | `roles`에 `superuser`가 있는 사용자 |
| 도메인 수신자 | 도메인에서 파생된 role을 가진 사용자. 예시 화면은 `test.com`을 `testcom`으로 표현 |

이 내용은 PDF에 제시된 후보 계약이며, 실제 운영 API의 권한·응답·도메인 role 생성 규칙을 이번 문서 작업에서 호출해 검증한 것은 아니다.

## 3. 현재 코드 대조

| ID | 현재 상태 | 판정 |
|----|-----------|------|
| FEEDBACK-001 | 4xx는 `WEB_ERROR_MIN_REQUESTS`, 5xx는 `SERVER_ERROR_MIN_REQUESTS`를 사용하며 기본값은 각각 20이다. 공통 판정이 Job의 탐지 여부와 최종 알림 변환에서 요청 수 하한과 오류율을 함께 검사한다. | 반영됨, 자동 테스트 통과·실서버 QA 필요 |
| FEEDBACK-002 | 메일은 `Content-Type: text/plain; charset=utf-8` 한 종류로 만들어지며 HTML 본문 필드가 없다. | 미구현 |
| FEEDBACK-003 | `SMTP_TO` 전체 수신자와 `SMTP_DOMAIN_RECIPIENTS` 정적 매핑은 있으나 Elastic 사용자 API 조회는 없다. 도메인 수신자를 고른 뒤 전체 알림 배열로 한 본문을 만들어 타 도메인 내용이 섞일 수 있다. | 부분 구현 및 확인된 정보 격리 결함 |

`enabled`는 PDF의 샘플 응답 필드이며 활성 사용자만 발송 대상으로 삼으라는 동작은 본문에 직접 적혀 있지 않다. 비활성 사용자 제외는 잘못된 발송을 막기 위해 추가한 파생 안전 요구사항이다.

## 4. 반영한 요구사항과 상태

- 4xx와 5xx 각각에 설정 가능한 최소 요청 수 조건을 추가했으며 기본값은 각각 20이다. 두 값은 별도 환경 변수로 관리한다.
- 최소 요청 수 판정은 Job의 `detected`와 `src/app.ts`의 알림 변환 필터에 같은 공통 판정으로 적용했다.
- 저표본, 정확한 하한·오류율 경계값, 도메인별 독립 적용에 대한 자동 테스트는 통과했으며 실제 서버·SMTP 회귀 QA는 남아 있다.
- 메일은 구조화된 HTML과 읽을 수 있는 plain-text 대체 본문을 함께 제공하도록 요구한다.
- HTML에 삽입되는 도메인, 경로, IP, 오류 사유 등 동적 값은 이스케이프하도록 요구한다.
- Elastic 사용자 API의 후보 계약을 문서화하고 `superuser` 전체 수신, 도메인 role별 제한 수신을 목표 동작으로 등록한다.
- 사용자별 알림 목록을 먼저 필터링한 후 제목과 본문을 생성하는 보안 경계를 유지한다.

## 5. 남은 결정 사항

1. 최소 요청 수 미만 집계를 로그·메트릭에는 남길지 여부
2. 기존 SMTP에서 직접 multipart HTML을 만들지, Resend API·템플릿을 채택할지
3. 도메인을 role로 바꾸는 정규화 규칙. 특히 점 제거만으로 발생할 수 있는 충돌 처리
4. role과 `hostDomain`의 정확 일치, 별칭, 와일드카드 허용 범위
5. 사용자 API 조회 주기·캐시·타임아웃과 장애 시 서비스 사용자 발송 정책
6. 사용자 API 호출 계정의 최소 권한과 비밀정보 주입 방식

상세 요구사항과 QA 케이스는 [요구사항 대시보드](../requirements-definition.md)와 [탐지·알림 회귀 QA 계획](../test-plans/2026-07-06-detection-regression.md)을 따른다.
